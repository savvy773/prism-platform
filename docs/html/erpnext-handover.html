01 / SCOPE

현재는 WSL 연습 환경입니다.

구성 확인 · 2026-09-18

Windows PC prismjuns 안의 WSL에서 Docker Compose로 실행합니다. ERPNext는 Frappe 프레임워크 위의 ERP 앱이며, Python 백엔드와 브라우저 UI, Node.js 실시간 연결, Redis 작업 큐, MariaDB가 협력합니다. 포털은 별도의 Next.js 앱입니다.

ERPNext 16.35.0Frappe 16.34.0 · 이미지에 포함MariaDB 11.8.9Redis 8.10.1포털 앞 공통 프록시: Traefik 3.7.13

지금 접속

ERPNext http://prismjuns:8080 ↗이름 연결 실패 시 192.168.123.66:8080 ↗

계정: Administrator
비밀번호 위치: environments/development/apps/.env의 ERP_ADMIN_PASSWORD. 문서에는 비밀번호를 복사하지 않습니다.

구현 범위

데모 회사·고객·품목·판매 주문, Excel 입출력 연습, 서비스 시작/중지, 앱별 데이터 초기화를 확인했습니다.

Ubuntu prismdev / ssh su는 배포 대상입니다. 운영 배포·Cloudflare Tunnel·커스텀 ERP 앱은 아직 구현 전입니다. 고급 위키·업무 기능은 포털에서 추가합니다.

02 / TOP DOWN

웹 요청이 처리되는 경로

컨테이너 수와 외부 포트 수는 다릅니다. ERP는 외부 웹 포트 하나로 접속합니다.

i

프록시 두 역할을 구분합니다. 현재 공통 Traefik은 TCP 80의 포털 요청을 처리합니다. ERP 요청은 8080으로 ERP 내부 Nginx에 직접 도달합니다. 향후 공통 프록시가 포털·ERP 호스트명을 나누도록 확장합니다.

05 / DAILY OPERATIONS

담당자가 사용하는 명령

개발 PC의 WSL 터미널 · 저장소 루트에서 실행

cd ~/code/prism-platform
make up                       # 전체 시작
make ps                       # 앱과 DB 상태
make stop MODULE=erpnext       # ERP 7개 서비스만 중지
make erp-demo                 # ERP 다시 시작 · 기존 데이터 유지
make logs MODULE=erpnext      # ERP 백엔드 로그 · Ctrl+C는 로그 보기만 종료
make down                     # 전체 중지 · 데이터 유지
ERP 시작 순서
  1. WSL·개발 환경·로컬 Docker·고정 프로젝트 이름을 검사하고 기존 비밀 설정을 유지합니다.
  2. 독립 MariaDB와 ERP 전용 Redis를 시작하고 준비 상태를 기다립니다.
  3. configurator가 공통 설정을 작성합니다. create-site는 사이트가 없을 때만 생성합니다.
  4. 최초 설정에 연습 회사와 샘플 데이터를 생성합니다. 기존 사이트에는 반복 초기화를 하지 않습니다.
  5. ERP 서비스 7개를 실행하고 frontend HTTP와 Redis 준비 상태를 확인합니다. 이어서 브라우저 로그인·업무 동작을 사람이 확인합니다.
연습 데이터를 지우고 새로 시작할 때만
make reset-dev MODULE=erpnext

ERP 사이트 DB를 재설치하고 공개·비공개 첨부파일과 전용 Redis를 비운 다음 데모를 다시 생성합니다. 포털 DB는 유지합니다. 입력한 ERP 연습 자료도 사라집니다. 운영용 명령이 아니며, Ubuntu 운영 서버에서는 개발 스크립트가 실행을 거부합니다.

make down은 이 프로젝트에서 중지를 뜻합니다. Docker의 볼륨 삭제 옵션을 실행하지 않습니다. 공유 DB만 중지하면 포털과 ERP가 모두 영향을 받습니다.

06 / DATA EXCHANGE

Excel 가져오기·내보내기

Import · 데이터 입력

  1. ERPNext 검색에서 Data Import를 엽니다.
  2. 대상 DocType(예: Item)과 추가/수정 방식을 선택합니다.
  3. 해당 대상의 템플릿을 내려받아 필수 값과 연결된 코드·이름을 채웁니다.
  4. XLSX를 올려 검증 결과를 확인한 뒤 가져오기를 실행합니다.
  5. 대상 목록을 새로 열어 저장된 값을 확인합니다.

Export · 데이터 확인

  1. Data Export에서 대상 DocType과 필요한 필드를 고릅니다.
  2. 필터와 파일 형식을 확인해 내보냅니다.
  3. Excel에서 한글·날짜·숫자·참조 값을 확인합니다.
  4. 재업로드할 파일은 ID와 필수 열을 유지합니다.

현재 샘플 품목을 실제 XLSX로 가져온 뒤 내보낸 값을 읽는 검증을 수행했습니다. 모든 업무 유형의 필드·권한이 동일한 것은 아닙니다.

참고: 공식 Data Import · 공식 Data Export

07 / MAINTENANCE

최신 상태를 유지하는 방법

ERPNext 16 · MariaDB 11.8 · Node 24 LTS · Redis 8 · Traefik 3의 검증 계열을 기준으로 합니다.

make check-updates            # 공식 배포처에서 호환 범위 최신 버전 조회
make update-stack             # 변경이 있을 때 검증·백업·업데이트

새 버전이 있으면 프로젝트 버전과 lockfile을 갱신하고 포털 빌드·검증을 수행합니다. 쓰기 서비스를 멈춘 뒤 기존 DB 덤프와 ERP 사이트 파일을 보관하고, 이미지 변경·ERP 스키마 마이그레이션·앱 재시작을 진행합니다. 중간에 서비스가 잠시 중단됩니다. 이미 최신이면 아무것도 변경하지 않습니다.

백업과 실패 시 대응

업데이트 전 스냅샷: ~/.local/state/prism/stack-backups/<UTC시각>/. DB 전체 덤프, ERP 사이트 파일, 변경 전 버전 파일과 업데이트 계획을 저장합니다. 현재 WSL에 남는 사본이며 정기 외부 백업이나 검증된 운영 복구 시스템을 대신하지 않습니다.

DB 변경 전 실패하면 버전 파일을 되돌립니다. DB 변경 후 실패하면 자동으로 구버전 DB를 실행하지 않고 멈춥니다. 에러 로그와 스냅샷을 보존하고, 별도 복구용 DB·볼륨에서 이전 이미지 및 SQL·사이트 파일의 복구를 검증해야 합니다. 운영 복구 자동화는 다음 단계입니다.

Git은 비밀값과 DB를 저장하지 않습니다. 원래 환경 설정도 함께 보관해야 합니다. 큐의 실행 중 작업은 복구 후 중복 실행 여부를 확인합니다.

이 명령은 프로젝트/Docker 스택용입니다. Windows·Ubuntu OS나 호스트의 apt 패키지를 일괄 업데이트하지 않습니다. ERPNext·Traefik의 새 메이저 버전은 호환 정책을 검토한 후 적용합니다. ERP 이미지 내부 Python/Node는 벤더 구성을 따릅니다.

08 / TROUBLESHOOTING

증상부터 확인할 위치까지

브라우저에서 ERP에 연결되지 않음

make ps로 frontend와 backend 상태를 봅니다. WSL에서 curl -fsS http://127.0.0.1:18081/api/method/ping를 실행해 앱 응답을 확인합니다. 내부 응답이 있고 다른 PC에서만 실패하면 이름 해석 → Windows 포트 전달 → 방화벽 순으로 확인합니다. 접속 안내의 IP 주소로도 비교합니다.

화면은 열리지만 긴 작업·가져오기가 멈춤

worker / scheduler / queue 상태를 확인합니다. 현재는 워커 하나가 모든 큐를 처리하므로 긴 작업 하나가 처리 시간을 늘릴 수 있습니다.

docker logs --tail 100 prism-dev-apps-erpnext-worker-1
docker logs --tail 100 prism-dev-apps-erpnext-scheduler-1
docker logs --tail 100 prism-dev-apps-erpnext-queue-1
실시간 진행률만 갱신되지 않음

websocket 로그와 프록시의 WebSocket 전달을 확인합니다. 새로고침으로 데이터가 보인다고 해서 실시간 경로가 정상이라는 뜻은 아닙니다.

docker logs --tail 100 prism-dev-apps-erpnext-websocket-1
DB 연결 오류 / 포털도 동시에 실패

공유 MariaDB 상태·디스크 공간·네트워크를 우선 확인합니다. 비밀번호를 임의로 바꾸거나 DB 볼륨을 지우지 않습니다. SQL 오류와 접속 오류를 구분합니다.

make db-status ENV=development DB=mariadb
make db-logs ENV=development DB=mariadb
docker system df
업데이트 이후 오류 / 초기화 실패

명령 출력에서 첫 실패 단계를 확인합니다. 초기화와 업그레이드는 다릅니다. 업그레이드 오류를 해결하기 위해 초기화를 실행하면 자료가 사라집니다. 전후 버전, 실패 명령, 시각, 컨테이너 로그, 스냅샷 위치를 기록해 담당자에게 전달합니다.

09 / EVOLUTION & HANDOVER

효율적으로 확장하고, 사람이 이어받기

커스터마이징 경계

설정·Custom Field·Customize Form으로 해결할 수 있는 범위를 먼저 사용합니다. 코드가 필요한 변경은 별도 Frappe 커스텀 앱과 재현 가능한 이미지 빌드로 관리하고, ERPNext 원본을 컨테이너 안에서 직접 고치지 않습니다.

커스텀 앱의 코드·fixtures·마이그레이션을 Git에 관리합니다. 포털의 위키·일정·주간보고·인수인계는 포털이 소유하고, ERP와 필요한 데이터만 API 계약으로 연결합니다.

다음 운영 단계

Ubuntu용 운영 이미지·재시작 정책 → 인증·권한 → 외부 백업과 복구 연습 → 호스트별 프록시 라우팅 → HTTPS·Cloudflare Tunnel → 로그·알림·CI 배포 순으로 진행합니다.

처리량이 늘면 short / long 워커를 나누고 수를 조정합니다. 요구가 생기는 부분부터 확장하며 공통 CSS·폰트·설정을 재사용합니다. 프록시는 HTTP·WebSocket 계약을 지키면 다른 제품으로 교체할 수 있게 둡니다.
