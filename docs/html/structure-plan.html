    Git은 DB·첨부파일·비밀번호가 담긴 .env를 보관하지 않습니다. 비밀 설정은 별도로 안전하게 보관합니다. DB 백업은 엔진의 백업 도구로 만들며, 실행 중인 DB 파일을 단순 복사하는 방식으로 대신하지 않습니다.

    DAILY OPERATIONS · 사용 가능

    실행 · 재생성 · 초기화를 구분합니다.

    코드만 바꿨을 때

    수정 → 재빌드 → 재생성

    개발 중에는 소스 연결과 자동 새로고침을 사용합니다. 배포 시 새 이미지를 빌드하고 앱 컨테이너를 교체합니다.

    유지: DB 데이터 · 첨부파일
    make dev / make rebuild MODULE=portal
    앱을 잠시 껐다 켤 때

    앱 중지 → 다시 실행

    개발 앱을 중지한 뒤 다시 실행합니다. 독립 DB 스택은 계속 실행되고, 앱은 기존 데이터에 다시 연결합니다.

    유지: DB 데이터 · 첨부파일
    make stop → make dev
    샘플 데이터부터 다시 시작할 때

    개발용 앱 데이터 초기화

    명시한 앱의 개발 DB와 전용 파일만 초기화하고 스키마·샘플 데이터를 재생성합니다. 다른 앱의 DB는 유지합니다.

    초기화: 선택한 개발 앱만 · 운영 사용 금지
    make reset-dev MODULE=portal

    RESET BOUNDARY

    예: 포털만 초기화하면 어디까지 바뀔까?

    Ubuntu su · 별도 환경

    운영 환경

    컨테이너·DB·볼륨·비밀 설정을 WSL과 별도로 둡니다. 개발 초기화는 WSL의 로컬 Docker만 대상으로 합니다.

    개발 초기화로 서버 데이터는 바뀌지 않습니다. SSH 배포는 테스트를 통과한 커밋을 명시해 별도로 실행합니다.

    초기화 스크립트에서 호스트·Docker 연결·개발 프로젝트를 확인하고 운영 대상을 거부합니다.

    FIRST VERIFICATION · 가짜 자료로 확인

    글 하나로 보존 범위를 직접 확인합니다.

    1. 테스트 글 작성포털에 테스트 글 저장
    2. 컨테이너 재생성저장한 글이 남는지 확인
    3. 포털만 초기화기존 데이터 제거 · 샘플 생성
    4. 분리 상태 확인ERPNext 테스트 데이터 유지

    데이터 복원은 별도 검증: DB·첨부파일 백업 → 테스트 데이터 변경 → 백업 복원 → 앱에서 내용 확인.

    DEPLOYMENT LOOP

    WSL에서 검증한 버전을 서버로.

    1WSL 개발코드 수정·실행
    →
    2Windows 테스트prismjuns에서 확인
    →
    3Git에 저장커밋·푸시
    →
    4SSH 앱 배포검증한 커밋 지정
    →
    5서버 접속 확인Windows에서 테스트

    Git push만으로 배포되지는 않습니다. 개발 DB를 서버에 덮어쓰지 않으며, 배포 시 필요한 스키마 변경은 별도로 적용합니다. 코드를 이전 버전으로 되돌려도 DB 변경까지 자동으로 복원되지는 않습니다.

    !

    앱 재생성과 DB 삭제는 별개입니다. 공용 DB 볼륨에는 여러 앱의 DB가 들어 있습니다. 특정 앱을 초기화하려고 DB 볼륨 전체를 지우지 않습니다. 개발 명령은 사용할 수 있습니다. Ubuntu 배포는 아직 구현 전입니다.
